# 媒体文件整理器 - 功能需求要点

> 本文档基于 Python 源码逐文件分析提炼，作为代码迁移到其他语言的功能需求基准。

---

## 一、总体架构

### 1.1 分层架构

| 层次 | 职责 | Python 对应模块 |
|------|------|----------------|
| **GUI 层** | 用户界面、交互、预览、菜单 | `enhanced_gui_pyside6_standalone.py`、`image_preview_manager.py`、`magic_tools.py`、`config_editor_dialog.py` |
| **控制器层** | 协调 UI 与业务逻辑、信号传递 | `gui_controller.py` |
| **业务服务层** | 分析/执行编排、单进程与多进程分发 | `business_service.py` |
| **核心逻辑层** | 文件扫描、日期提取、日期范围校验、失败文件管理、报告生成 | `core.py` |
| **提取器层** | 多策略日期提取（EXIF/ExifTool/FileName/FileSystem/HEIF） | `extractors/` 目录下 6 个文件 |
| **文件操作层** | 按日期分级目录创建、copy/move/link、重名处理 | `file_ops.py`、`multiprocess_file_operator.py` |
| **多进程层** | 进程池并行提取、MD5 计算、日志合并 | `multiprocess_processor.py` |
| **配置层** | JSON 配置管理、跨平台路径、提取器/模式配置 | `config.py`、`config.json`、`patterns.json` |
| **日志层** | 精简/详细双模式、SQLite 文件指纹、操作历史、去重查询 | `log_manager.py` |
| **辅助层** | 文件名结构指纹、正则变体生成、多语言 | `pattern_analyzer.py`、`languages.py` |

### 1.2 核心数据流

```
用户选择源目录 → 扫描文件(按扩展名过滤) → 多提取器加权投票提取日期
→ 日期范围校验(过去N年/未来缓冲天数) → 成功文件写入 detail_config.json
→ 失败文件写入 unparsed_files.json → 生成分析报告(TXT)
→ 用户选择操作类型 → 按日期分级创建目录 → copy/move/link 执行
→ 失败文件可单独移动到指定文件夹
```

## 二、功能需求详解

### 2.1 文件扫描

| 需求项 | 说明 |
|--------|------|
| **扫描源目录** | 递归扫描源目录下所有文件 |
| **扩展名过滤** | 仅处理 `supported_formats` 配置的扩展名（jpg/png/tiff/bmp/webp/heic/heif/mp4/mov/avi/mkv/wmv/flv/webm/m4v/mpg/mpeg/3gp/3g2 等） |
| **扫描所有文件** | 可选配置 `scan_all_files=true`，忽略格式限制扫描所有文件 |
| **进度报告** | 每处理 `progress_interval` 个文件更新一次进度 |

### 2.2 日期提取（核心功能）

#### 2.2.1 提取器体系

系统采用**多提取器加权投票**机制，按权重从高到低依次尝试，取第一个有效结果。

| 提取器 | 权重(默认) | 数据来源 | 支持格式 |
|--------|-----------|----------|----------|
| **EXIF 提取器** | 1.2 | PIL 读取 EXIF 标签 (DateTimeOriginal 36867 / DateTimeDigitized 36868 / DateTime 306) | jpg/png/tiff/bmp/webp |
| **ExifTool 提取器** | 1.2 | 纯 Python 方案：HEIC 用 pyheif、视频用 hachoir/mutagen/PIL 降级、标准图片用 PIL | HEIC/视频/标准图片 |
| **文件名提取器** | 1.1 | 正则模式匹配文件名中的日期信息 | 所有文件 |
| **文件系统提取器** | 0.8 | 文件修改时间 mtime | 所有文件（默认禁用） |
| **HEIF 提取器** | 1.0 | pyheif + PIL 专用 HEIC 提取 | HEIC/HEIF |

#### 2.2.2 提取器公共校验逻辑

每个提取器共享 `_is_valid_date` 校验：
- 日期范围：`1970-01-01` ~ `2100-12-31`
- 最大过去年数限制：`max_years_past`（默认 30，即不早于当前年份 - 30）
- 未来日期缓冲：`future_date_buffer_days`（默认 0 = 不允许未来日期；> 0 允许指定天数内的未来日期）
- 校验失败的日期视为无效，继续尝试下一个提取器

#### 2.2.3 文件名提取器的正则模式匹配

**模式配置结构**（`patterns.json`）：
```json
{
  "name": "模式名称",
  "pattern": "正则表达式",
  "group_mapping": { "year": 1, "month": 2, "day": 3, "hour": 4, "minute": 5, "second": 6 },
  "ignored_groups": [],
  "timestamp_length": 13,  // 可选，时间戳位数
  "enabled": true,
  "weight": 1.0
}
```

**支持的日期格式类型**：
- 通用日期时间格式：`2024.01.15.14.30.00` → year/month/day/hour/minute/second
- 10 位 Unix 时间戳（秒级）
- 13 位时间戳（毫秒级，如微信导出）
- 16 位时间戳
- 微信导出格式：`mm_export + 13位时间戳`
- 小红书格式
- OPPO 手机格式
- 年月日格式：`2024-01-15`、`2024_01_15`、`20240115`
- 年月日时分秒格式：`20240115143000`
- 其他自定义正则模式（用户可扩展）

**快速年份扫描策略**：先扫描文件名中是否存在合理的 4 位年份（1970-当前年份+缓冲），不存在则快速跳过，避免对每个文件执行全部正则。

#### 2.2.4 提取器工厂

- 根据配置动态创建提取器实例
- 注入 `max_years_past`、`future_date_buffer_days` 参数
- 注入 `patterns.json` 模式列表给文件名提取器
- 只创建 `enabled=true` 的提取器

### 2.3 文件分析与处理流程

#### 2.3.1 分析阶段（analyze）

1. 扫描源目录，获取文件列表
2. 对每个文件依次执行启用的提取器，取第一个有效日期
3. 成功提取日期的文件 → 记录到 `detail_config.json`（按日期分组）
4. 失败文件 → 记录到 `unparsed_files.json`
5. 生成分析报告（TXT 格式）
6. 支持单进程或多进程模式

**detail_config.json 结构**：
```json
{
  "metadata": { "source_dir": "...", "total_files": 100, "success_count": 80, "failed_count": 20 },
  "files": {
    "2024-01-15": {
      "photo.jpg": { "path": "/full/path", "date_source": "EXIF", "size": 1234567 }
    }
  }
}
```

**unparsed_files.json 结构**：
```json
{
  "metadata": { "total_unparsed": 20 },
  "files": [
    { "filename": "unknown.xyz", "path": "/full/path", "reason": "No valid date found" }
  ]
}
```

#### 2.3.2 执行阶段（execute）

1. 读取 `detail_config.json`，遍历所有已成功提取日期的文件
2. 按日期创建分级目录结构（见 2.4）
3. 根据操作类型执行文件操作（见 2.5）
4. 处理同名文件（见 2.5）
5. 未来日期文件归入特殊文件夹 `FutureDate`
6. 可选：将失败文件移动到指定文件夹

### 2.4 目录分级结构

| 配置值 | 目录结构示例 |
|--------|-------------|
| `year` | `2024/` |
| `month` | `2024/01/` |
| `day`（默认） | `2024/01/15/` |

- 配置项 `classification_level` 控制
- 未来日期文件统一放入 `FutureDate/` 文件夹

### 2.5 文件操作

| 操作类型 | 说明 |
|----------|------|
| **copy** | 复制文件到目标目录，保留原文件 |
| **move** | 移动文件到目标目录 |
| **link** | 创建硬链接/符号链接（取决于操作系统） |

**同名文件处理策略**：
| 策略 | 说明 |
|------|------|
| **skip** | 跳过，不处理同名文件 |
| **overwrite** | 覆盖目标文件 |
| **rename** | 自动重命名，追加 `_1`、`_2` 等序号 |

**文件修改时间矫正**：
- 可选将文件 mtime 设置为提取到的日期，便于资源管理器排序

### 2.6 多进程处理

| 需求项 | 说明 |
|--------|------|
| **启用条件** | 配置 `enable_multiprocess=true`，建议文件数 > 1000 时启用 |
| **进程数** | `multiprocess_num`（0 = 自动检测 CPU 核心数） |
| **批量大小** | `multiprocess_batch_size`，每个进程一次处理的文件数量 |
| **进程池任务** | 并行提取日期、计算 MD5（详细模式） |
| **临时日志合并** | 各进程独立写临时 SQLite 日志，完成后合并到主 `file_registry.db`（WAL 模式） |
| **单进程回退** | 多进程失败时自动回退到单进程模式 |

### 2.7 日志与数据库

#### 2.7.1 双模式

| 模式 | 特点 |
|------|------|
| **精简模式 (simple)** | 仅内存日志，不计算 MD5，不写数据库，速度快 |
| **详细模式 (detailed)** | 计算 MD5 文件指纹，写入 SQLite 数据库，支持去重和统计 |

#### 2.7.2 SQLite 数据库结构（详细模式）

**files 表（文件指纹）**：
- `id`, `md5` (UNIQUE), `path`, `filename`, `size`, `mtime`
- `date_extracted`, `date_source`, `category`, `status` (active/failed), `updated_at`
- 索引：md5、path、date_extracted

**extraction_results 表（提取器结果）**：
- `id`, `file_id` (FK), `extractor_name`, `weight`
- `result_date`, `in_range`, `valid`, `error`

**operation_history 表（操作历史）**：
- `id`, `operation_type`, `source_path`, `target_path`, `reason`, `timestamp`, `reversible`

#### 2.7.3 日志功能

| 功能 | 说明 |
|------|------|
| **记录文件处理** | 文件名、路径、成功/失败、提取日期、日期来源、提取器结果列表 |
| **记录操作历史** | 操作类型、源路径、目标路径、原因 |
| **查询文件** | 按 MD5、日期范围、分类、状态过滤查询 |
| **查找重复文件** | 按 MD5 分组，找出 count > 1 的文件，计算浪费空间 |
| **导出日志** | 支持 JSON 和 CSV 格式导出 |
| **内存日志上限** | 最多保留 1000 条内存日志 |

### 2.8 分析报告

#### 2.8.1 文件分析报告（TXT）

分析完成后自动生成，内容包括：
- 源目录、输出目录
- 总文件数、成功数、失败数、成功率
- 按日期来源统计（EXIF/FileName/ExifTool 等）
- 按年份/月份的文件分布统计
- 操作类型（copy/move/link）
- 失败文件列表（文件名 + 失败原因）

#### 2.8.2 正则模式分析报告

- 模式总数、启用数、禁用数
- 重复正则表达式检测
- 潜在冲突检测（相同捕获组数量的模式）
- 模式使用情况统计（各模式匹配次数和百分比）
- 优化建议（禁用模式清理、通配符+时间戳警告、权重调整建议）

| **失败文件列表** | 从 `unparsed_files.json` 加载，显示文件名和路径 |

| **失败文件移动** | 可配置目标文件夹，将失败文件批量移动到指定位置 |
| **单独处理** | 对单个失败文件进行日期修改、EXIF 编辑、重命名等操作 |
| **处理后同步** | 修改后自动同步更新 JSON 文件中的记录 |

## 三、非功能需求

### 3.1 性能

| 需求项 | 说明 |
|--------|------|
| **大文件处理** | MD5 计算使用 8KB 分块读取，避免内存溢出 |
| **多进程加速** | 文件数 > 1000 时建议启用多进程，充分利用多核 CPU |
| **SQLite WAL 模式** | 详细模式数据库使用 WAL 提高并发写入性能 |
| **批量提交** | 数据库每 100 条记录提交一次 |
| **内存日志限制** | 最多 1000 条内存日志，防止内存溢出 |
| **进度更新节流** | 按配置间隔更新进度，避免频繁 UI 刷新 |

### 3.2 健壮性

| 需求项 | 说明 |
|--------|------|
| **编码处理** | JSON 文件统一 UTF-8 编码，CSV 导出使用 UTF-8-SIG（兼容 Excel） |
| **异常降级** | 多进程失败自动回退单进程；ExifTool 降级到 PIL；HEIC 降级到 pyheif |
| **路径处理** | 路径规范化 `os.path.normpath`，跨平台兼容 |
| **文件存在检查** | 操作前检查文件是否存在 |
| **数据库初始化** | 使用 `CREATE TABLE IF NOT EXISTS`，幂等创建 |
| **资源释放** | 数据库连接在析构函数中确保关闭 |

### 3.3 可扩展性

| 需求项 | 说明 |
|--------|------|
| **提取器插件化** | 抽象基类 `DateExtractor`，新增提取器只需继承并实现 `extract` 方法 |
| **提取器工厂** | 按配置动态创建提取器，支持启用/禁用和权重调整 |
| **正则模式可扩展** | 用户可通过魔术工具添加自定义正则模式 |
| **多语言可扩展** | `LANGUAGE_MAP` 字典结构，新增语言只需添加键值对 |
| **配置热加载** | 配置修改后可保存并重新加载 |

## 五、迁移注意事项

### 5.1 平台相关功能

| 功能 | Python 实现 | 迁移注意 |
|------|------------|----------|
| **文件链接** | `os.link()` / `os.symlink()` | 不同 OS 的链接行为差异（Windows 需管理员权限） |
| **系统应用打开** | `os.startfile()` (Win) / `open` (Mac) / `xdg-open` (Linux) | 需按目标语言平台的 API 实现 |
| **文件修改时间** | `os.utime()` | 大多数语言有等价 API |
| **进程池** | `multiprocessing.Pool` | 目标语言的并发模型可能不同 |
| **SQLite** | `sqlite3` 标准库 | 目标语言需引入 SQLite 驱动 |

### 5.2 核心算法迁移要点

| 算法 | 说明 |
|------|------|
| **加权投票提取** | 按权重降序排列提取器，依次尝试，取第一个有效结果 |
| **文件名结构指纹** | 将文件名每个字符分类为 D(数字)/L(字母)/S(符号)，生成指纹字符串用于排序 |
| **智能正则变体生成** | 多文件名逐字符对比，相同部分为 FIXED，不同部分按数字/非数字分流生成 `\d{n}` 或通配符 |
| **日期范围校验** | `当前年份 - max_years_past ≤ 提取年份 ≤ 当前日期 + future_date_buffer_days` |
| **重名处理** | `skip` 跳过 / `overwrite` 替换 / `rename` 追加 `_n` 序号 |

### 5.3 数据格式兼容

迁移后应保持以下数据格式兼容：
- `config.json` 结构和字段名
- `patterns.json` 模式结构
- `detail_config.json` / `unparsed_files.json` 结构
- SQLite 数据库表结构（`file_registry.db`）
- 分析报告 TXT 格式
