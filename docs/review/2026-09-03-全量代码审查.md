## 二、P0：功能性失效

### P0-1 「移动 move」选项的启用条件写反 —— 移动端 move 永久不可用

[WorkbenchView.axaml:167](../../src/MediaOrganizer.Android/Views/WorkbenchView.axaml)

```xml
<ComboBoxItem Content="移动 move" IsEnabled="{Binding !IsMoveAllowed}"/>
```

`IsMoveAllowed = !isNetwork`（[WorkbenchViewModel.cs:163](../../src/MediaOrganizer.Shared/ViewModels/WorkbenchViewModel.cs)）。取反后语义完全颠倒：**本地目标时"移动"被禁用，网络目标时反而可选**。同文件 129 行的网络提示条用 `!IsMoveAllowed` 是对的；桌面端同一处写的是 `IsEnabled="{Binding IsMoveAllowed}"`（[Desktop/WorkbenchView.axaml:91](../../src/MediaOrganizer.Desktop/Views/WorkbenchView.axaml)）——可确认是移植时误加了 `!`。

后果：FR-A5 的 move 在移动端等于失效。网络侧因 `UpdateNetworkState()` 有 `if (isNetwork && OperationIndex == 1) OperationIndex = 0` 兜底，不至于真按 move 执行。

**修法**：删掉那个 `!`。

### P0-2 目录扫描跑在 UI 线程 —— 大目录必 ANR

[Analyzer.cs:26-35](../../src/MediaOrganizer.Core/Analysis/Analyzer.cs) ← [WorkbenchViewModel.cs:278](../../src/MediaOrganizer.Shared/ViewModels/WorkbenchViewModel.cs)

`AnalyzeAsync` 是 async 方法，但 `_scanner.Scan(sourceDir)` 位于**第一个 await（`Parallel.ForEachAsync`）之前**，因此在调用线程同步执行。调用链 `AnalyzeCommand`（UI 线程）→ `_session.AnalyzeAsync` → `analyzer.AnalyzeAsync` 全程没有 `Task.Run`。

* 真实路径模式：`Directory.EnumerateFiles` 递归数万文件，UI 冻结数秒；

* SAF 模式更糟：[AndroidFileScanner.Walk](../../src/MediaOrganizer.Android/Platforms/AndroidFileScanner.cs) 每目录一次 `ListFiles()`、每文件三次 `Name/Length/LastModified`，全是 Binder IPC → **必然 5s ANR**；

* 附带效应：UI 卡死期间「取消」按钮点不动（排在同一消息队列后面）。

**修法**：`WorkbenchViewModel.AnalyzeAsync` 改 `await Task.Run(() => _session.AnalyzeAsync(...), ct)`；或在 `Analyzer.AnalyzeAsync` 开头把 `Scan` 包进 `Task.Run`（对双端都有收益，`Progress<T>` 的回调线程语义不受影响）。

### P0-3 「多变体生成」产出的正则永远无法命中

[PatternInferrer.cs:180-209](../../src/MediaOrganizer.Core/Patterns/PatternInferrer.cs) → [MagicToolsViewModel.cs:392-399](../../src/MediaOrganizer.Desktop/ViewModels/MagicToolsViewModel.cs)

`GenerateVariantRegex` 逐位输出 `Regex.Escape(ch)` / `\d{1}` / `.`，**全程不产生任何捕获组**。回到 `TestRegex` → `PatternInferrer.Infer`：`m.Groups.Count == 1`（只有组 0）→ 命名组循环不执行 → `map.Count == 0` → 位置推断要求 `n == 1` 或 `n >= 3`，而 `n == 0` → `GroupMapping` 保持为空。再进 `PatternEngine.TryExtract`：无 `timestamp` 键，`Group("year", -1)` 返回 -1 → `year < 1` → 返回 null。

结果：**全部样本显示"未命中"**，而 `SavePattern` 要求 `TestResults.Any(t => t.Matched)` → 用户永远存不下来。FR-7.4 多变体智能生成功能性失效。

附带：`minLen = samples.Min(s => s.Length)` 会把长样本的尾部整段丢弃。

**修法**：把连续的差异位合并成一个 `(\d{n})` 捕获组并回填 `GroupMapping`；相同位合并为 `x{n}` 而非逐字符重复。

### P0-4 「初始化默认配置」后设置页 UI 完全不刷新

[SettingsViewModel.cs:180-196](../../src/MediaOrganizer.Shared/ViewModels/SettingsViewModel.cs)（`LoadFromConfig`）+ [:207-216](../../src/MediaOrganizer.Shared/ViewModels/SettingsViewModel.cs)（`Initialize`）

`LoadFromConfig()` 为规避即时落盘副作用，**直写 backing field 并** **`#pragma warning disable MVVMTK0034`**：

```csharp
_maxYearsPast = _config.Extraction.MaxYearsPast;
_supportedFormatsText = string.Join(", ", _config.Scan.SupportedFormats);
...
```

在构造函数里这样做是安全的（还没有绑定）。但 `Initialize`（桌面「初始化默认配置」按钮，[Desktop/SettingsView.axaml:15](../../src/MediaOrganizer.Desktop/Views/SettingsView.axaml)）**复用了同一个方法**，此时控件已绑定 → 不触发 `PropertyChanged` → 年份回溯 / 未来缓冲 / 进度间隔 / 并发数 / 扩展名白名单 / 主题 / 窗口尺寸 / 预览尺寸**全部显示旧值**，与已落盘的新配置不一致。用户再动其中任一控件，就会把"旧值"当新值写回。

**修法**：给 `LoadFromConfig` 加 `bool notify` 参数，`Initialize` 走属性赋值路径（或在末尾逐个 `OnPropertyChanged(nameof(...))`）。

### P0-5 「初始化默认配置」后提取器列表指向被丢弃的旧配置

同上 `Initialize`

`ResetConfigToDefaults` 用 `config.Extraction = defaults.Extraction` **整体换实例**，但 `Extractors` 这个 `ObservableCollection` 是在构造函数里一次性建好的，`Initialize` 从不重建它。于是：

* UI 上提取器的勾选/权重仍是重置前的值；

* 用户拖动权重 → `OnExtractorChanged` 按 `Name` 去**新的** `_config.Extraction.Extractors` 里找并写入 → 界面与配置从此长期打架。

**修法**：`Initialize` 末尾清空并重建 `Extractors`（记得先解绑旧 VM 的 `PropertyChanged`），与 `RefreshPatterns()` 对齐。

## 三、P1：高

### P1-1 分析链路上另有两处 UI 线程阻塞 IO

| 位置                                                                                                | 内容                                                                                                                                                  |
| ------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| [OrganizeSession.cs:96-105](../../src/MediaOrganizer.Core/OrganizeSession.cs)                     | `AnalysisResultStore.Save`（全量 JSON 序列化）+ `AnalysisReportGenerator.Generate` + `File.WriteAllText`。上游 await 未 `ConfigureAwait(false)`，续体回到 UI 线程     |
| [FailedFilesViewModel.cs:203](../../src/MediaOrganizer.Shared/ViewModels/FailedFilesViewModel.cs) | `PendingFileMover.MoveAsync` 直接 await，无 `Task.Run`；其中 `File.Exists`/`FileInfo.Length`/`Delete`/`Directory.CreateDirectory` 全为同步调用，批量移动数百文件时 UI 持续掉帧 |

另：[ReportViewModel.Set](../../src/MediaOrganizer.Shared/ViewModels/ReportViewModel.cs) 会把 `AnalysisReportGenerator.Generate` **再跑一遍**（Session 刚为落盘生成过一份，内容完全相同）→ 每次分析在 UI 线程做两次全量分组统计。建议 Session 缓存生成好的报告文本供 `Set` 取用。

### P1-2 SAF 选取 / 另存超过 60 秒 → 进程崩溃

[MainActivity.cs:104](../../src/MediaOrganizer.Android/MainActivity.cs)

```csharp
return tcs.Task.WaitAsync(TimeSpan.FromSeconds(60));   // 超时抛 TimeoutException
```

三个调用方：[AndroidStorageAccess.EnsureAsync](../../src/MediaOrganizer.Android/Platforms/AndroidStorageAccess.cs) **catch 了**（说明作者已知此坑）；[SafFolderPicker.cs:22](../../src/MediaOrganizer.Android/Platforms/SafFolderPicker.cs) 与 [AndroidFileSaver.cs:19](../../src/MediaOrganizer.Android/Platforms/AndroidFileSaver.cs) **没 catch**。

异常沿 `BrowseSourceCommand` / `SaveReportCommand` 冒泡。`AsyncRelayCommand` 默认把失败重抛到同步上下文（未启用 `FlowExceptionsToTaskScheduler`）→ 用户在系统文件选择器里翻目录超过 1 分钟再回来 = **崩溃**，且刚选的目录还会被静默丢弃（`WaitAsync` 已放弃该结果）。

**修法**：`StartForResultAsync` 去掉超时（Activity 结果回调可靠，`_pending` 单条会被同 requestCode 覆盖），或在两个调用方按 `EnsureAsync` 的方式吞掉 `TimeoutException` 返回 null。

### P1-3 未来日期缓冲天数从未传给规划器 —— 校验与归档口径不一致

[OrganizeSession.cs:138](../../src/MediaOrganizer.Core/OrganizeSession.cs)

```csharp
CurrentPlan = new ArchivePlanner(_level).Plan(_result, _outputRoot);
```

`ArchivePlanner(ClassificationLevel level, int futureDateBufferDays = 0, ...)` 的第二个参数**在生产代码里从未传值**，恒为 0。而 `DateRangeValidator` 是从配置正常拿到 `FutureDateBufferDays` 的（[ExtractorChain.cs:24](../../src/MediaOrganizer.Core/Extraction/ExtractorChain.cs)）。

于是当用户把「未来缓冲」设为 1 或 7 天（两端设置页都暴露了这个开关）：校验器认为明天的照片**合法**（不进失败清单），规划器却按 buffer=0 判定 `date.Date > now.Date` → 归到 **`FutureDate/`**。`ArchivePlanner` 的 XML 注释明写"与 DateRangeValidator 同标准（FR-5.4/FR-2.4 一致）"，实际不一致。

值得注意的是 [ArchivePlannerTests.cs:45,57](../../test/MediaOrganizer.Core.Tests/ArchivePlannerTests.cs) **显式传了** **`futureDateBufferDays: 1`** 并断言通过——测试覆盖了参数，却没覆盖接线，属于典型的"绿灯假象"。

**修法**：`new ArchivePlanner(_level, _config.Extraction.FutureDateBufferDays)`，并补一条"从 Session 走到底"的集成测试。

### P1-4 正则缓存无界 + `RegexOptions.Compiled` —— 魔术工具每敲一个键泄漏一个编译正则

[PatternEngine.cs:17-24](../../src/MediaOrganizer.Core/Patterns/PatternEngine.cs)

```csharp
private static readonly ConcurrentDictionary<string, Regex?> RegexCache = new();
... new Regex(p, RegexOptions.Compiled | RegexOptions.CultureInvariant)
```

对固定的 patterns.json 这是对的（预编译热路径）。但魔术工具是**实时测试**：[`OnRegexTextChanged`](../../src/MediaOrganizer.Desktop/ViewModels/MagicToolsViewModel.cs) [→](../../src/MediaOrganizer.Desktop/ViewModels/MagicToolsViewModel.cs) [`TestRegex`](../../src/MediaOrganizer.Desktop/ViewModels/MagicToolsViewModel.cs) [→](../../src/MediaOrganizer.Desktop/ViewModels/MagicToolsViewModel.cs) [`PatternEngine.TryExtract(name, pattern)`](../../src/MediaOrganizer.Desktop/ViewModels/MagicToolsViewModel.cs)，用户每敲一个字符就产生一个新的中间态正则并被永久缓存。`RegexOptions.Compiled` 会生成动态方法/程序集，**运行期不可卸载**。编一条 40 字符的正则 = 40 个编译正则常驻。

**修法**：给 `TryExtract` 加一个"不缓存/不编译"的重载供魔术工具调用；或按 `pattern.Name` 而非 pattern 字符串做键并限制缓存容量。

### P1-5 提取器权重滑块拖一次 = 写盘几十次 + 反复失效分析计划

[SettingsViewModel.cs:467-478](../../src/MediaOrganizer.Shared/ViewModels/SettingsViewModel.cs) + [Desktop/SettingsView.axaml:32](../../src/MediaOrganizer.Desktop/Views/SettingsView.axaml)、[Android/SettingsView.axaml:62](../../src/MediaOrganizer.Android/Views/SettingsView.axaml)

`Slider` 未设 `IsSnapToTickEnabled`，`Value` 双向绑到 `Weight` → 拖动过程中每个像素都触发 `OnExtractorChanged`：

```csharp
_state.SaveConfig(notifyChanged: false);   // 原子写：临时文件 + File.Move
_state.NotifyChanged();                    // → Workbench.RebuildChain → InvalidateResult
```

一次拖动 = 几十次"创建临时文件 + 原子改名"，并把已有的分析结果反复置为失效。移动端触屏拖动更密集。

**修法**：Slider 加 `IsSnapToTickEnabled="True" TickFrequency="0.1"`，并给权重变更做防抖（例如 300ms）或改为 `LostFocus`/拖动结束时提交。

### P1-6 桌面「批量移动」进度条一开始就是满的

[Desktop/FailedFilesView.axaml:27](../../src/MediaOrganizer.Desktop/Views/FailedFilesView.axaml)

```xml
<ProgressBar Value="{Binding MoveProgress}" Maximum="1" .../>
```

而 VM 里是 `MoveProgress = p * 100`（[FailedFilesViewModel.cs:202](../../src/MediaOrganizer.Shared/ViewModels/FailedFilesViewModel.cs)，取值 0\~100）。`Maximum="1"` → 第一个文件移完就 100%。Android 侧同一处写的是 `Maximum="100"`（正确）。

**修法**：桌面改 `Maximum="100"`。

### P1-7 用系统应用打开：`ResolveActivity` 前置检查会误判

[AndroidSystemFileOpener.cs:33-37](../../src/MediaOrganizer.Android/Platforms/AndroidSystemFileOpener.cs)

targetSdk 36，受 Android 11 起的软件包可见性过滤约束，而清单没有 `<queries>` 声明 → `PackageManager.ResolveActivity` 结果被过滤可能返回 null；而 `startActivity` 走系统解析**不受该限制**。于是"能打开也报没有应用能打开"，FR-A6.3 在部分机型/文件类型上直接失效。

**修法**（更简且代码更少）：删掉 `ResolveActivity` 分支，直接 `StartActivity` 并 catch `ActivityNotFoundException` 后弹 Toast。

### P1-8 抽屉角标刷新可能把当前页面弹回工作台

[MainViewModel.cs:111-112](../../src/MediaOrganizer.Android/ViewModels/MainViewModel.cs) + [MainView.axaml:110](../../src/MediaOrganizer.Android/Views/MainView.axaml)

`NavItem` 是 record，角标变化时整条替换 `NavItems[1] = NavItems[1] with { Badge = value }`；而 ListBox 的 `SelectedIndex` 与 `SelectedPage` 是 TwoWay。选中项被 Replace 时选择模型按"移除+插入"处理，`SelectedIndex` 落到 -1 并回写 `SelectedPage = -1` → `CurrentPage` 落入 `_ => Workbench`，标题也变回"整理工作台"。触发条件：停在「失败文件」页时角标数字变化。

Avalonia 12 的 Replace 选择行为我未能真机验证；但即使选择未被清空，`SelectedItem` 也会变成已被丢弃的旧实例。

**修法**（很便宜）：`NavItem` 改成 `ObservableObject` + `[ObservableProperty] Badge`，原地改属性不换实例。

## 九、确认无问题（不要顺手"优化"）

审下来这些地方是对的，且多数是历史踩坑后的定型写法：

* **`JsonFileStore`** **原子写**：临时文件 + `File.Move(overwrite)` + 按路径串行锁 + 损坏隔离，完整闭环（修掉了 08-30 评审 2.5）。

* **Keystore 加密**（`AndroidCredentialCrypto`）：GCM IV 前置拼接、tag 128 位、加密失败抛异常而非静默存空密码，且与 `CredentialCrypto` 的 `KS:`/`DPAPI:`/`B64:` 前缀约定自洽。

* **`FileOperator`** **的** **`.mo-tmp`** **→ 大小校验 → rename** 与 `AndroidSafStorage.MoveAsync` 优先 `DocumentsContract.RenameDocument` 的配合：临时名与终名恒同目录，前提成立。

* **`_targetGates`** **在 finally 统一 Dispose**、**SMB storage 的** **`using`**、**`ReplacePreview`** **释放旧 Bitmap**、**`WebDavFileStorage._knownDirs`** **用 ConcurrentDictionary**：都是已修好的资源/并发问题。

* **`DateRangeValidator`** **按"日"取上界**（`upperDay.AddDays(1).AddTicks(-1)`）：08-30 评审 2.2 的正确修法。

* **`LogsViewModel`** **用** **`Dispatcher.UIThread.Post`** 处理跨线程日志追加。

* **`LocalFileStorage.Resolve`** **的路径穿越防护**（`..` 逃出根目录时抛异常）。

* **`App.axaml`（Android）的字体处理**：`FontFamily` 元素不能写 `{StaticResource}`、Selector 必须写 `TextElement.FontFamily`——注释记录的两个坑都是真的。

* **Android csproj 那批构建开关**（`EmbedAssembliesIntoApk` / `AndroidUseDaemonAapt2=false` / 单 RID）与 **Desktop 的** **`PrunePublishOutput`**：注释详实且都对应真实故障。
