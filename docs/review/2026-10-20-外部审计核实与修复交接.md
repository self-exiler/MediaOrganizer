## 三、批次 A：数据正确性（优先，每条 1–15 行）

### A1. 统一按本地时间归档（审计 1）

**现状**
- `src/MediaOrganizer.Core/Patterns/PatternEngine.cs:114-130` `TimestampToDate`：`FromUnixTimeMilliseconds/Seconds` 返回的 `DateTimeOffset` 偏移量为 0（UTC）。
- `src/MediaOrganizer.Core/Sources/LocalMediaSource.cs:22-25, 40-41`：`ModifiedTime` 同样以 `TimeSpan.Zero` 构造。
- 对比：文件名年月日分支（`PatternEngine.cs:105-106`）用 `LocalTz.GetUtcOffset` 生成本地偏移 —— 同一批文件两种口径。
- `src/MediaOrganizer.Core/Planning/ArchivePlanner.cs:35-45` `BuildRelative` 直接 `date.Year/Month/Day`，未转本地。

**修复规格**
在 `ArchivePlanner.BuildRelative` 入口统一 `var local = date.ToLocalTime();`，后续 `Year/Month/Day` 与 `date.Date > now.Date` 的 FutureDate 判定全部改用 `local`。
（选在规划层而不是各源头修，是为了一次性覆盖所有提取器；`now` 是 `DateTimeOffset.Now`，比较基准同为本地，语义自洽。）

**验收**
- 单元测试：UTC+8 下，`ModifiedTime` 为 `2024-01-01T02:00:00+08:00`（UTC 2023-12-31 18:00）的文件，目标目录必须是 `2024/01/01`，不是 `2023/12/31`。
- 毫秒/秒级时间戳文件名（如 `mm_export1704067200000.jpg`）同样归入本地日期。

### A2. Overwrite 的删除时机（审计 2）

**现状**
`src/MediaOrganizer.Core/Execution/FileOperator.cs:170-186` `ResolveCollisionAsync`：
```csharp
case ExistAction.Overwrite:
    await _target.DeleteAsync(relativeTarget, ct);   // ← 传输还没开始
    return new CollisionResolution(relativeTarget, CollisionAction.Overwrite);
```
删除发生在 `TransferWithRetryAsync`（:188-236）之前。网络中断且三次重试失败时，旧文件已删、新文件未落盘。

**修复规格**
1. `ResolveCollisionAsync` 的 Overwrite 分支不再删除，只返回带 `Action=Overwrite` 与标记的 resolution（可给 `CollisionResolution` 加一个 `bool DeleteBeforeMove` 字段，或在传输方法里直接判 `_existAction == Overwrite`）。
2. 在 `TransferWithRetryAsync` 中，临时文件写完、大小校验通过后、调用 `MoveAsync(temp, finalTarget, ct)` **之前**执行 `_target.DeleteAsync(finalTarget, ct)`。
3. 保留现有「先写 `.mo-tmp` 再改名」的自证流程不变。

**验收**
- 模拟 `CopyFromAsync` 连续三次抛异常：目标端原有文件必须仍然存在（不被删）。
- Overwrite 成功路径：旧文件被新内容替换，计数 `Overwritten` 仍 +1。

### A3. 同名互斥闸改为忽略大小写（审计 3）

**现状**
`src/MediaOrganizer.Core/Execution/FileOperator.cs:73-76`
```csharp
var duplicatedTargets = files.GroupBy(f => f.RelativeTarget)   // 默认比较器：区分大小写
```
`_targetGates`（:42）同为默认比较器。`IMG.JPG` 与 `img.jpg` 得到两把不同的闸，可并发执行；但它们共用同一个 `.mo-tmp`（在大小写不敏感的 FS 上是同一文件），第二个先失败重试，最终 `MoveAsync` 落到已存在的文件上。
`src/MediaOrganizer.Core/Storage/LocalFileStorage.cs:76-84` `MoveAsync`：`if (File.Exists(to)) File.Delete(to);` —— 无条件先删后移，于是 Skip/Rename 策略下也会静默覆盖一张照片。

**修复规格**
1. `duplicatedTargets` 的 `GroupBy` 与 `ToHashSet` 加 `StringComparer.OrdinalIgnoreCase`。
2. `_targetGates` 的 `ConcurrentDictionary` 构造加 `StringComparer.OrdinalIgnoreCase`。
3. **不要动** `_targetGates` 的锁结构本身（本轮不做分组重构）。

**验收**
- 同目录构造 `IMG.JPG` 与 `img.jpg` 两个源，ExistAction=Skip：成功 1、跳过 1，目标端不得出现覆盖。
- ExistAction=Rename：得到 `IMG.jpg` 与 `img.jpg` 两个不同文件（或平台允许的去重结果），不得丢文件。

### A4. WebDAV 存在检查与大小校验（审计 4）

**现状**
`src/MediaOrganizer.Core/Storage/WebDavFileStorage.cs`
- `:46-54` `ExistsAsync`：吞掉 `WebDAVException`（错误码 404 **或 0**）与 `HttpRequestException`，一律返回 `false`。瞬时网络故障 → 判定「不存在」→ 走无碰撞分支 → `MoveAsync`（`:111-112`，`overwrite: true`）覆盖已有文件。Skip 策略形同虚设。
- `:95-106` `CopyFromAsync`：`return source.Length;` —— 直接返回源长度，`FileOperator` 里 `actual != expected` 的比较对 WebDAV 恒为真，校验形同虚设。

**修复规格**
1. `ExistsAsync`：只把 **404** 当作不存在；错误码 0、HTTP 异常、其他状态码一律向上抛出（由 `FileOperator` 的三层退避重试接管）。
2. `CopyFromAsync`：上传成功后调用 `GetLengthAsync(relativeTarget, ct)` 回查实际长度并 `return`；回查返回 `-1` 或与 `source.Length` 不等时抛 `IOException`。
3. 注意：`CreateDirectoryAsync`（`:57-80`）内部复用了 `ExistsAsync` 判断目录是否存在——改严格后要确认建目录路径不会因为非 404 错误而抛异常中断；如需要，为目录判断另写一个宽容版本（失败即视为不存在并尝试创建，靠 `WebDAVConflictException` 兜底）。

**验收**
- 注入一次 `HttpRequestException`：`ExistsAsync` 必须抛异常（不是返回 false），且上层重试后成功。
- 注入一个「上传后长度不符」的场景：必须计入失败清单，不得静默通过。

### A5. 紧凑日期抢匹配（审计 5）

**现状**
`src/MediaOrganizer.Core/Configuration/PatternsStore.cs`
- `:79-83`「紧凑日期」`(\d{4})(\d{2})(\d{2})`，权重 **0.8**，无数字边界。
- `:84-89`「秒级时间戳」权重 0.7、`:99-102`「毫秒级」0.7、`:103-108`「微秒级」0.6 —— 都带 `(^|[^0-9])…([^0-9]|$)` 边界。
- `src/MediaOrganizer.Core/Extraction/FileNameExtractor.cs:28-31`：命中即返回，不校验、不回溯。

后果：13 位毫秒时间戳的前 8 位若恰好凑成合法月/日（概率 ≈ 12/100 × 31/100 ≈ 3.7%），会被解析成 16xx/17xx 年的「合法日期」并返回；时间戳模式根本没机会运行；后续范围校验拒绝该结果 → 文件进失败列表。

**修复规格（双管齐下，缺一不可）**
1. 给内置紧凑类模式加数字边界：`(?<!\d)(\d{4})(\d{2})(\d{2})(?!\d)`（同步处理 `:72-77`「紧凑日期时间」`(\d{4})(\d{2})(\d{2})[ _]?(\d{2})(\d{2})(\d{2})` 的边界，注意它要求 14 位数字，13 位时间戳天然不匹配，但为一致性仍应加）。
2. **把日期合理性校验下放到提取层**：`FileNameExtractor` 的循环里，对 `TryExtract` 返回的结果先做范围校验（年份落在 1970–2100、且通过现有 `DateRangeValidator` 的语义），不通过则**继续尝试下一个模式**，而不是直接返回。
   - 这一步是关键：用户已有的 `patterns.json` 不会自动更新内置正则，只改内置模式挡不住旧配置文件。
3. 可选加固：`PatternEngine`（`:95-111`）在年月日分支对 `year < 1970 || year > 2100` 直接返回 `null`，让循环自然继续。

**验收**
- 造 1000 个 2020–2026 年的毫秒时间戳文件名，全部解析为正确的本地日期，失败率 0（修复前约 3.6%）。
- 正常 `20240115`、`IMG_20240115_143022` 等文件名解析不变。

### A6. 魔术工具与运行时的文件名口径统一（审计 6）

**现状**
- `src/MediaOrganizer.Desktop/ViewModels/MagicToolsViewModel.cs:437, 449`：测试用 `Path.GetFileNameWithoutExtension`。
- `src/MediaOrganizer.Core/Extraction/FileNameExtractor.cs:24`：运行时用 `file.FileName`（**含扩展名**）。
- `src/MediaOrganizer.Core/Patterns/PatternInferrer.cs:156-159`：日期在末尾时生成的正则以 `$` 收尾，运行时被 `.mp4` 挡住。

3. `PatternInferrer` 生成时若以 `$` 收尾，需与运行时口径一致（两者都去扩展名后即自洽）。

**验收**

## 六、执行者须知：本机环境约束

来自本仓库的踩坑记录，照做可省数小时：

- **构建**：Desktop 走 `net10.0`；Android 只能构建 `MediaOrganizer.Android.csproj`，**禁止**对 `slnx` 用 `-f net10.0-android`（NETSDK1005）。本机 dotnet **没有 android 工作负载**，Android 只能走 VS 或 CI。
- **XARDF7024**：命令行改 csproj 属性后易撞（SDK 清理 lp 目录重复加 `\\?\` 前缀）→ `rm -rf obj/Debug/net10.0-android/lp` 后重建（约 6–7 分钟）。
- **git push 本机必败**（`CRYPT_E_NO_REVOCATION_CHECK`，MITM 代理）。唯一可用命令：
  `git -c http.sslVerify=false -c http.proxy=http://127.0.0.1:11719 push origin main`
  不要尝试 schannelCheckRevoke / openssl 后端 / SSH，均无效。
- **CI 验证**：`gh run watch <id> --exit-status`；`gh run view --log-failed | grep error` 抓错。编译错误分阶段暴露，需迭代几轮。
- **发版**：打 `v*` tag 推送即触发 release.yml。
- **OneDrive**：工作区在 OneDrive 下，`.git` 可能被云占位抽走 pack 数据导致仓库假死；发现异常按 `MEMORY.md` 里的恢复套路处理。
- 不要删除 `.workbuddy/` 目录。
