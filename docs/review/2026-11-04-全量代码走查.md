# 2026-11-04 全量代码走查（Android GUI 修复后）

## 这个仓库做什么

MediaOrganizer 是 .NET 10 / Avalonia 12 的媒体文件整理工具：递归扫描照片与视频、按拍摄日期生成「年/月/日」归档计划，再复制或移动到本地目录、SMB、WebDAV。Core（整理逻辑）与 Shared（ViewModel）被桌面端和 Android 端共用，两端各自组合根注入平台服务。

**假设负载**：单人使用，一次整理 1 千～5 万个文件，目标常为 NAS / WebDAV；桌面端单进程，Android 端靠前台服务跑数小时的大批量任务。按 5 万文件这个量级判断规模问题，不按多用户服务判断。

## 复核方式

四路分模块走查共给出 77 条候选。本轮对拟写入报告的 20 条逐条回读源码、全树 grep 引用；其中「输出目录设盘符根」用临时 .NET 10 程序实跑验证。未逐条复核的候选不进清单，核实为误报的单独列在文末。**2026-11-04 全量修复实施时又发现 #12 属误判，已撤销该条改动并在此更正；其余 19 条已落地。**

## Must fix（9 条）

### 1. 覆盖同名文件时先删旧、后改名，失败即新旧俱失
- **现象**：`ExistAction.Overwrite` 下，`FileOperator.TransferWithRetryAsync` 把新数据写进 `.mo-tmp` 后先 `DeleteAsync(finalTarget)` 删旧文件，再 `MoveAsync`。
- **问题**：改名因网络抖动/服务端拒绝抛异常时，catch 里 `TryDeleteTempAsync(temp)` 把新数据也删掉，重试耗尽后目标端两个文件都没有。而 SMB 的 `ReplaceIfExists=true` 与 WebDAV 的 `overwrite:true` 本身已支持原子覆盖，前置删除纯属多余。
- **修复**：删掉 `FileOperator.cs:180-181`；`LocalFileStorage.MoveAsync` 把「先删后移」合并成 `File.Move(from, to, overwrite: true)`；改 `BatchARegressionTests` 里把有害行为锁成断言的那条用例。
- **不修的后果**：弱网 NAS 上一次覆盖失败，用户永久丢失该文件。
- **证据**：`Core/Execution/FileOperator.cs:180-190`、`Core/Storage/LocalFileStorage.cs:76-83`、`Core/Storage/WebDavFileStorage.cs:134-135`（已读）；`SmbFileStorage.cs:432-440`（走查定位，未逐行复核）。

### 2. 输出目录设为盘符根，整次归档 100% 失败
- **现象**：`LocalFileStorage.Resolve` 用 `Path.TrimEndingDirectorySeparator(Root) + '\\'` 做前缀校验。
- **问题**：.NET 对根目录 `D:\` 不移除尾分隔符，于是 `rootPrefix = "D:\\"`，而 `full = "D:\2024\01\01\a.jpg"` 既不匹配前缀也不等于 Root，每个文件都抛「目标路径越出输出根目录」。
- **修复**：改用 `Path.GetRelativePath(Root, full)` 不以 `..` 开头判定，或比较 `Root` 结尾是否已是分隔符。
- **不修的后果**：用户把输出选成 `D:\` 时全批失败，且报错指向完全无辜的路径校验。
- **证据**：`Core/Storage/LocalFileStorage.cs:20-24`；临时程序实跑输出 `root=D:\ prefix=D:\\ full=D:\2024\01\01\a.jpg accepted=False`，普通目录 `accepted=True`。

### 3. 权限引导带 `FLAG_ACTIVITY_NEW_TASK`，全新安装首次点「选取」必然无反应
- **现象**：`AndroidStorageAccess.EnsureAsync` 用 `StartForResultAsync` 启动「所有文件访问」设置页，却给 Intent 加了 `ActivityFlags.NewTask`。
- **问题**：以 NEW_TASK 启动的 Activity 会立即回调 `RESULT_CANCELED`；此时 `HasAllFilesAccess` 仍是 false，`EnsureAsync` 返回 false，`PickFolderAsync` 直接返回 null。用户被丢到设置页，授权后必须再点一次。
- **修复**：删掉 `intent.AddFlags(ActivityFlags.NewTask)` 一行，回调 + 权限复查已自洽。
- **不修的后果**：首次使用体验是「选目录按钮点了没反应」。
- **证据**：`Android/Platforms/AndroidStorageAccess.cs:22-34`、`MainActivity.cs:110-122`。

### 4. `<root-path>` 把整机文件系统暴露给 FileProvider
- **现象**：`file_paths.xml` 除 `external-path` 外还声明了 `<root-path name="root_storage" path="." />`。
- **问题**：`ToFileProviderUri` 对任意绝对路径都能生成 content URI 并带读权限交给第三方 App。若 identifier 指向应用私有目录的 `config.json`（含 Keystore 加密凭据、NAS 地址与用户名），即可被分享出去。
- **修复**：删掉 `root-path` 一行；确需 SD 卡则按具体卷名单列 `external-path`。
- **不修的后果**：私有配置与凭据存在外泄通道。
- **证据**：`Android/Resources/xml/file_paths.xml:6`、`Android/Platforms/AndroidSystemFileOpener.cs:16-35`（走查定位）。

### 5. 前台服务「停止」绕过宿主终态，任务卡住时永久卡死
- **现象**：`ActionCancel` 分支只调 `host.Cancel()` 就 `FinalizeAndStop()`（撤前台、发「已停止」通知、`StopSelf`）；`OrganizeJobHost.End()` 只在 `RunJobAsync` 的 finally 执行。
- **问题**：任务若卡在不受 CancellationToken 控制的 SMB 同步 socket，`await job()` 不返回，`End()` 不执行 → `_running` 恒 true、WakeLock/WifiLock 不释放、`IsBusy` 恒 true，之后每次开始任务都被「已有任务在运行」拒绝，而用户已看到「任务已停止」通知。
- **修复**：`FinalizeAndStop` 里补一个宿主 `ForceFinish(outcome)`（置 `_running=false`、释放锁、触发 `Finished`），并让 `End()` 幂等；`ActionCancel` 分支只留 `host.Cancel()`。
- **不修的后果**：弱网下 App 进入必须强杀进程才能恢复的假死状态。
- **证据**：`Android/Platforms/OrganizeForegroundService.cs:39-44,79-97`、`OrganizeJobHost.cs:178-198`（已读）；`OnTimeout` 属同类路径，未逐行复核。

### 6. `MainActivity._pending` 是实例字段，Activity 重建后 SAF 回调永久挂起
- **现象**：`_pending` 保存 SAF 选目录 / 另存为 / 权限页的回调，`OnActivityResult` 靠它了结 Task。
- **问题**：配置变更（语言、字体缩放、外接键盘等未列入 `ConfigurationChanges`）或内存回收导致 Activity 重建时，新实例的 `_pending` 为空，悬挂的 `TaskCompletionSource` 永不完成，`PickFolderAsync`/`SaveTextAsync`/`EnsureAsync` 的等待方僵住。代码只处理了「同一请求码重复发起」。
- **修复**：`_pending` 改为 `static readonly`（与进程级 `Instance` 同生命周期），`OnDestroy` 里以 null 了结悬挂项。
- **不修的后果**：旋转/切语言后目录选取按钮永久无响应。
- **证据**：`Android/MainActivity.cs:56,101-122`（已读）。

### 7. `MoveToPending` 在 await 确认弹窗之前不置忙碌态
- **现象**：守卫 `if (Items.Count == 0 || IsMoving) return;` 之后，先 `await _confirm.ConfirmAsync(...)`，第 242 行才 `IsMoving = true`。
- **问题**：弹窗等待期间按钮仍可点，第二次调用通过同一守卫，两个确认各自起一个 `PendingFileMover` 对同一批文件「复制 + 删除源」，源文件被删两次、目标重名、失败清单不可信。
- **修复**：把 `IsMoving = true` 上移到守卫之后、await 之前，并扩大 try/finally 覆盖范围。
- **不修的后果**：双击按钮即产生重复文件与虚假失败记录。
- **证据**：`Shared/ViewModels/FailedFilesViewModel.cs:220-275`、`Desktop/Views/FailedFilesView.axaml:25`。

### 8. 输出目标配置被写坏：改名不同步 + 瞬时 `-1` 落盘
- **现象**：`SaveNetwork` 编辑分支只替换 `NetworkProfiles[idx]`，不更新 `_config.Paths.OutputNetworkProfile`；`ReloadOutputTargets` 用 `Math.Max(0, 1 + FindIndex(...))`，名字找不到时得 0；`OnOutputTargetIndexChanged` 无条件 `SaveConfig`。
- **问题**：① 把当前选中的网络位置改名后，配置里仍是旧名，UI 显示「本地目录」，执行时 `StorageFactory.CreateTarget` 按旧名找不到 profile 直接抛异常；② `State.Changed` 重建下拉 ItemsSource 时 ComboBox 回写 `SelectedIndex=-1`，把已持久化的网络目标清空并落盘。
- **修复**：改名时同步写 `OutputNetworkProfile`；`OnOutputTargetIndexChanged` 首行 `if (value < 0) return;`，持久化改由 `SaveNetwork`/`DeleteNetwork` 显式负责。
- **不修的后果**：用户勾选一条文件名规则就可能把输出目标改成看不见的旧网络名，执行必失败。
- **证据**：`Shared/ViewModels/SettingsViewModel.cs:382-409`、`Shared/ViewModels/WorkbenchViewModel.cs:161-181`、`Core/StorageFactory.cs:27-30`（均已读）。

### 9. WebDAV `GetLengthAsync` 吞掉所有异常，且会删掉已上传成功的数据
- **现象**：`GetLengthAsync` 用裸 `catch { return -1; }`；`CopyFromAsync` 上传成功后回查长度，回查失败即抛「无法回查大小」。
- **问题**：① 401/断网/取消都被吞成 `-1`，`TestConnectionAsync` 把认证错误误报成「目标文件大小异常」；② 上传其实已成功，异常冒泡到 `FileOperator` 后又触发 `TryDeleteTempAsync` 清理，把刚上传的数据删掉（同第 1 条窗口）。
- **修复**：只把 404 映射为 -1，其余（尤其 `OperationCanceledException`）原样上抛；上传后校验改用 `CopyFromAsync` 返回的写入字节数自证。
- **不修的后果**：认证失败时报错误导，偶发回查失败时文件被静默删除。
- **证据**：`Core/Storage/WebDavFileStorage.cs:100-128`、`Core/StorageFactory.cs:35-50`、`Core/Execution/FileOperator.cs:185-190`（均已读）。

### 14. 重名探测无上界，且每次一次网络往返
- **现象**：`FindFreeAsync` 用 `for (var i = 1; ; i++)` 逐个 `ExistsAsync(candidate)`。
- **问题**：目标目录已有 M 个同名文件、再归档 N 个时，总往返约 `N·M + N²/2`；网络目标每次几十毫秒，100+100 个同名文件约 1.5 万次往返。若 `ExistsAsync` 持续返回 true（故障/缓存），循环无上界直到取消。
- **修复**：一次列目录拿到已占用的 `_n` 集合，内存算下一个空位；给 `i` 加基于目录条目数的上界。
- **不修的后果**：批量同名照片在 NAS 上耗时从分钟级涨到小时级。
- **证据**：`Core/Execution/NameCollisionResolver.cs:12-23`、`Core/Execution/FileOperator.cs:252-253`。

### 15. 视频 200MB 内存闸门按 CPU 核数并发放大
- **现象**：`MaxVideoBytesForTagRead = 200MB` 是单文件上限，不可 seek 流被整段拷进 `MemoryStream`；`Analyzer` 默认并行度是 `Environment.ProcessorCount`。
- **问题**：一批大视频并发即 1.6～3.2GB 托管内存 + LOH 碎片，Android 上直接 OOM。
- **修复**：闸门降到 32MB，并给视频提取单独 `SemaphoreSlim(1~2)` 限流。
- **不修的后果**：手机上整理一段 4K 视频目录时进程被系统杀死。
- **证据**：`Core/Extraction/ExifExtractor.cs:45-57`、`Core/Analysis/Analyzer.cs:22,36-37`。

### 16. UI 线程同步写盘，逐项勾选 O(n²)
- **现象**：勾选一条模式 `OnPatternChanged → SavePatterns()`，各设置项 `OnXxxChanged → Persist() → SaveConfig()`，全在 UI 线程做 `File.Create + Serialize + File.Move`；`UpdateSelectAllText` 每次勾选 `Items.All(...)`。
- **问题**：NumericUpDown 每跳一格就整文件重写 config.json；1000 个失败文件逐个勾选累计百万次求值。`_batchChecking` 只压住「全选」按钮，不覆盖逐项勾选。
- **修复**：落盘统一走 `OnExtractorChanged` 已有的 300ms 防抖；`UpdateSelectAllText` 改 `_checkedCount` 增量计数 O(1)。
- **不修的后果**：设置页与失败文件页在大批量下明显卡顿。
- **证据**：`Shared/ViewModels/SettingsViewModel.cs:485-491,570-587`、`FailedFilesViewModel.cs:113-124`。

### 18. 发版链路四处不一致
