# 评估:安卓系统字体切换可行性 + 扫描/执行并行度安全性

- 日期:2026-09-05
- 背景:① 测试者反馈并行度设为非自动时闪退;② 提出取消自打包字体改用系统字体以减小 APK。经查,当初自打包字体的动机(「汉语无法显示」)实为一处代码错误(用户确认),本评估据此重审。

---

## 1. 安卓系统字体:结论 = 支持切换,分两步走,预期 APK 减 3.5~5MB

### 1.1 史实还原(为什么当初打包字体)

| 时间点 | 事实 |
|---|---|
| 初版 5629327 | **即已打包** NotoSansSC-Regular.otf(8,331,336 字节 ≈ 7.94MB);同版 App.axaml 把 `ContentControlThemeFontFamily` 写成**元素内容形式** `<FontFamily>{StaticResource AppFont}</FontFamily>` |
| 缺陷机理 | Avalonia 中 `FontFamily` 元素内容按「字体族名字符串」解析、不展开标记扩展 → 资源值成为字面字符串 `{StaticResource AppFont}` → 非法字体族。反编译 Avalonia.Skia 12.1.1 证实:`FontManagerImpl.TryMatchCharacter` 会把该族名透传给 `SKFontManager.MatchCharacter(familyName, …)`(L121),**非法族名使按码点的系统回退一并失效** → 依赖该主题键的控件(Button/ComboBox 等)中文全部不可见,仅 ASCII 可见 |
| 修复 d1104aa | 改为 `avares://…#Noto Sans SC` URI 字面量 → Button/ComboBox 中文恢复。提交说明「修正 ContentControlThemeFontFamily 字体引用,Button/ComboBox 中文正常显示」 |
| 误诊 | 注释留下的「Avalonia 12 Android 系统字体回退缺陷致 CJK 空白」结论**从未被独立验证过**——应用从第一版就带着字体包,系统字体路径从未真正跑过。真凶即此代码错误(与用户结论一致) |

### 1.2 平台事实(反编译/包依赖核实,Avalonia 12.1.1)

- `Avalonia.Android 12.1.1` **依赖 `Avalonia.HarfBuzz 12.1.1`**(project.assets.json 闭包含该包)→ Android 端文本整形齐备,不存在桌面端曾出现的 "No text shaping system configured" 问题;
- `Avalonia.Skia.FontManagerImpl` 基于 `SKFontManager.Default`(Android 上即 Skia 的系统字体管理器,读 /system/etc/fonts.xml + /system/fonts),`TryMatchCharacter → MatchCharacter` 按码点回退路径存在且接入 Avalonia FontManager;
- 即:默认字体(Roboto/sans-serif)缺 CJK 字形时,标准回退链应命中系统 CJK 字体(荣耀:HarmonyOS/HONOR Sans;原生:Noto Sans CJK SC;小米:MiSans)。

### 1.3 两步切换方案(每步可独立回退)

> **实施记录(2026-09-06)**:两步已一次性完成——App.axaml 移除全部字体覆盖(留历史注释)、
> csproj 删除 AvaloniaResource 行、Fonts/NotoSansSC-Regular.otf 已删(git 可恢复)。
> 下次安卓构建即同时验证渲染与体积;若真机 CJK 空白,`git checkout HEAD~ -- src/MediaOrganizer.Android/App.axaml`
> 并 `git checkout HEAD~ -- src/MediaOrganizer.Android/Fonts` 即回退。WorkbenchView 统计卡
> Viewbox 防裁切修复同批验证。

**第一步(验证渲染,不动包体)**
- 删除 `App.axaml` 中 `AppFont`、`ContentControlThemeFontFamily` 两个资源与 `Control`/`TextBlock`/`AccessText` 三条 `TextElement.FontFamily` 样式;
- **保留** `Fonts/` 目录与 csproj 的 `<AvaloniaResource Include="Fonts\**" />(此时体积不变,纯验证);
- 真机验证清单(荣耀 PGT-AN10 + 至少一台非荣耀):
  1. 工作台/设置/报告全部页面中文完整(重点:Button/ComboBox/弹窗/通知文案/Popup 弹层);
  2. 分析结果里的**用户文件名**(含生僻字、emoji 命名的文件)显示正常;
  3. 混排(中文+ASCII+数字)基线与换行无明显异常;长文本省略号正常;
  4. 深浅主题下文字均可见。

**第二步(兑现体积)**
- 删除 `Fonts/` 目录 + csproj 的 AvaloniaResource 行 → 出包对比 APK 体积;
- 回退方式:git 还原 App.axaml / 目录即可,一处改动。

**若真机确有个别机型 CJK 空白(回退链真有缺陷时)**
- 方案 B:在组合根给 `FontManagerOptions.FontFallbacks` 显式列出系统 CJK 族名(`HONOR Sans`、`HarmonyOS Sans SC`、`MiSans`、`Noto Sans CJK SC`、`Source Han Sans SC`),仍不打包——命名族加载与自动按码点匹配是两条路径,前者更可控;
- 方案 C(兜底):维持现状打包,但可子集化(GB2312 常用集 ≈ 2MB)——注意生僻文件名场景依赖回退,子集化仅在回退可用时安全。

### 1.4 体积账与次级影响

- OTF 7.94MB 以 AvaloniaResource 嵌入 `MediaOrganizer.Android.dll` → APK 内为 `lib_MediaOrganizer.Android.dll.so`(ELF 封装、deflate 存储),OTF 典型压缩率 45~55% → **预计 APK 减 3.5~5MB(实测 50MB → 约 45~46.5MB,NFR-A3 上限 60MB)**;精确值以两步法出包对比为准;
- 次级影响(均为可接受/正向):
  - 各机型默认字体度量(行高/字宽)略有差异 → 布局自查一轮(文本换行、省略、按钮高度);
  - **emoji 反而恢复显示**(原 NotoSansSC 不含 emoji,旧注释专门提醒 UI 避开 emoji);
  - 拉丁走默认(Roboto)、中文走系统 CJK 的混排为安卓常态。

## 2. 扫描/执行并行度:结论 = 静态审查未发现「非自动值本身」的不安全路径

### 2.1 值域与守卫(全部消费点逐一核对)

| 环节 | 事实 |
|---|---|
| UI 值域 | 安卓 ComboBox 白名单 `[0,1,2,4]`(执行)/ `[0,1,2,4,8]`(扫描),索引→值映射,越界回退 0;桌面 NumericUpDown 0..64 |
| 配置回读 | 未知历史值经 `IndexOf` <0 → 0(自动),不会带出非法值 |
| Analyzer(扫描) | ctor `≤0 → Environment.ProcessorCount`;`Parallel.ForEachAsync` 的 ParallelOptions 合法 |
| OrganizeSession(执行) | `>0 ? 配置值 : (网络4/本地2)` |
| FileOperator | ctor `≤0 → 2` 归一 |
| 线程安全 | 提取器无状态;`AndroidExifReader` 每调用独立 `ExifInterface`;`PatternEngine` 只读静态 + `ConcurrentDictionary` 正则缓存;TagLib 每文件独立实例;FileOperator/SmbFileStorage 自有并发控制 |

**静态结论:1/2/4/8 这些值本身不会构造出崩溃路径;设置动作本身也只是 int 赋值 + SaveConfig(与其它设置项同路径)。**

### 2.2 测试者「非自动时闪退」的可能真因(按嫌疑排序,待真机取证)

1. **视频提取的内存峰值 × 并行度联动**:EXIF 提取器对 ≤200MB 的视频走「整文件读入 MemoryStream」做 TagLib 解析(`ExifExtractor.MaxVideoBytesForTagRead`)。DOP=8 并发命中多个大视频时内存峰值可达 GB 级 → Android 直接杀进程(表现即闪退,无 .NET 异常可捕获)。注意:4 核机上 auto=4 而显式选 8 时,显式值**确实**比 auto 更危险——与「非自动才出事」的报告吻合;
2. **本地目标拷贝缓冲**:LocalFileStorage 每路副本租 8MB 缓冲,DOP=8 → 64MB 峰值(次要);
3. 报告不精确:测试者版本、操作序列(设置后是分析崩还是执行崩)未知。

### 2.3 取证与加固建议

- 取证(换机测试时):`adb logcat -s Mono,DotNet,AndroidRuntime *:E` 下复现「设置非自动 → 分析/执行」,分别取 1/2/4/8 对比;崩溃时保留完整堆栈(`dotnet` 崩溃通常表现为 SIGSEGV/abort 或未处理异常);
- 可选加固(如证实为假设 1):给视频提取加「并发内存预算」(如同时在读的 TagLib 视频总字节数 ≤ 400MB,超出的排队),并让 LocalFileStorage 缓冲随 DOP 缩放;
- 与本轮后台化改造无交互:执行仍走同一 `OrganizeSession.ExecuteAsync` 路径,并行度语义未变。
