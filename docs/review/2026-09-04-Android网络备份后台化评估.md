# Android 网络备份：耗时分析与后台化方案评估

- 日期：2026-09-04
- 范围：`MediaOrganizer.Android`（targetSdk 36 / Android 16，实测机 Honor PGT-AN10）
- 目标：备份到网络端（SMB / WebDAV）耗时偏大，评估改为后台运行的可行方案
- 结论摘要：**「后台化」与「提速」是两件事**。后台化解决的是"必须一直盯着 App、退到后台就被杀"，**不会**让传输变快；真正的时间大头在网络往返次数与单流吞吐上，需要单独优化。建议分两条线并行推进。

---

## 1. 结论先行

| # | 结论 | 依据 |
|---|------|------|
| 1 | 现状执行链路完全跑在 Activity 进程内的后台线程，无前台服务、无通知、无任务落盘。退到后台/锁屏后进程随时可被回收，WakeLock 只保 CPU，不保进程、不保网络 | `WorkbenchViewModel.ExecuteFilesAsync` → `OrganizeSession.ExecuteAsync` → `Task.Run`；`MainViewModel.OnIsBusyChanged` 持 `WakeLockHolder` |
| 2 | **SMB 目标下设置的"执行并发数 4"完全无效**：`SmbFileStorage` 用单条 TCP 连接 + `SemaphoreSlim(1,1)` 串行化所有操作，4 个并行任务实际排队 | `SmbFileStorage.cs:36 / :123 InvokeAsync` |
| 3 | **单文件的固定 SMB 往返约 13~17 次**（不含数据块），这是除带宽外的最大开销；文件越多越明显 | 见 §3 逐行清单 |
| 4 | 已完成的文件即使中断也不会重传（默认 skip 策略会走 Exists 检查），所以**"断点续传"的边际价值主要在于省掉重跑时的检查开销与保留统计**，属于锦上添花而非刚需 | `FileOperator.ResolveCollisionAsync` |
| 5 | 跨会话执行目前是**硬阻塞**：分析结果落盘 JSON 不含 `MediaFile.Source`，回读后执行必然全失败 | `AnalysisResultStore.cs:7-9`、`FileOperator.cs:151-152` |
| 6 | 建议落地顺序：**M0 埋点测量 → M1 前台服务（性价比最高）→ M3 提速 → M2 断点续传** | 见 §6 |

## 2. 现状：执行链路与生命周期

```
[UI 线程] WorkbenchView 点击「执行」
        ↓
WorkbenchViewModel.ExecuteFilesAsync          (Shared/WorkbenshVM.cs:308)
        ├─ 快照选项到 session / 存配置
        ├─ _cts = new CancellationTokenSource()   ← 取消令牌挂在 VM 上（Activity 重建即失效）
        ├─ new Progress<double>(...)               ← 每文件完成都 Post 回 UI 线程刷新状态文本
        └─ await _session.ExecuteAsync(progress, ct)
                ↓
OrganizeSession.ExecuteAsync                  (Core/OrganizeSession.cs:163)
        ├─ using var storage = StorageFactory.CreateTarget(_config)   ← SMB：1 条 TCP 连接，全程复用
        ├─ parallelism = 配置值 或（网络 4 / 本地 2）
        └─ Task.Run(() => new FileOperator(...).ExecuteAsync(plan, progress, ct))
                        ↓
FileOperator.ExecuteAsync                     (Core/Execution/FileOperator.cs:41)
        └─ Parallel.ForEachAsync(files, MaxDegreeOfParallelism = 4)
                ├─ _targetGates[相对路径] 串行化同名检查+传输
                └─ ResolveCollision → CreateDirectory → CopyFrom → GetLength → Move → SetMtime
```

**进程生命周期现状**

| 维度 | 现状 | 风险 |
|------|------|------|
| 运行载体 | Activity 进程内的 `Task.Run` + 线程池 | 应用退后台后进程优先级降为 cached，系统可随时回收 |
| CPU 保活 | `PARTIAL_WAKE_LOCK`（4h 安全超时） | 只保 CPU；**Doze 下网络仍受限**，且进程仍可被杀 |
| 用户可见性 | 仅 App 内进度条 + 底部状态栏 | 锁屏/切走后完全无感知，也无法从通知拉回 |
| 通知权限 | `AndroidManifest.xml` **未声明 `POST_NOTIFICATIONS`** | Android 13+ 前台服务通知不会显示 |
| 任务状态 | 仅存在于 VM 内存（`_session`、`_cts`、计数器） | 进程死则全部丢失，无续跑能力 |
| 取消入口 | `CancelAnalysisCommand`（复用执行期的 `_cts`） | 依赖 VM 存活，退后台重建后点不到 |

## 3. 耗时构成分析

### 3.1 单文件的 SMB 往返清单（逐行读代码得出）

| 步骤 | 代码位置 | SMB 往返次数 |
|------|----------|------|
| `ExistsAsync`（同名检查） | `FileOperator.cs:124` → `SmbFileStorage.cs:153` | CreateFile 1 + Close 1 = **2** |
| `CreateDirectoryAsync`（按日分级 = 3 级，逐级创建、无缓存） | `FileOperator.cs:146` → `SmbFileStorage.cs:171` | 3 × CreateFile（+ 成功时 Close）= **3~4** |
| `CopyFromAsync` | `SmbFileStorage.cs:213` | CreateFile 1 + N × WriteFile + Close 1 = **2 + N** |
| `GetLengthAsync`（大小校验） | `FileOperator.cs:158` → `SmbFileStorage.cs:191` | CreateFile 1 + QueryInfo 1 + Close 1 = **3** |
| `MoveAsync`（含前置 `DeleteIfExists`） | `SmbFileStorage.cs:266` | (CreateFile+Close) 2 + CreateFile 1 + SetInfo 1 + Close 1 = **5** |
| `SetModifiedUtcAsync`（仅 FixMtime 开启） | `SmbFileStorage.cs:312` | **3** |
| **合计固定开销** | | **13~17 次往返**（FixMtime 关闭时 13~14） |

> 对照：`WebDavFileStorage` 已有 `_knownDirs` 目录缓存（`WebDavFileStorage.cs:16`），且底层 `HttpClient` 天然并发——**SMB 路径明显吃亏**，这解释了"网络备份慢"主要发生在 SMB 目标上。

### 3.2 量化模型

```
T_total ≈ Σ_files [ T_read + T_write + N_rtt × RTT ]
```

以 **5000 张 / 平均 4MB / 合计 20GB**、按日分级、FixMtime 关闭为例：

| 场景 | RTT | 数据写入（25MB/s 单流） | 固定往返开销 | 合计 |
|------|-----|----------------------|-------------|------|
| 局域网 WiFi 良好 | 2 ms | 800 s ≈ 13.3 min | 5000 × 14 × 2ms = 140 s ≈ 2.3 min | **≈ 15.6 min** |
| 弱信号 / 跨网段 | 10 ms | 800 s | 700 s ≈ 11.7 min | **≈ 25 min** |
| 远程 / 高延迟链路 | 25 ms | 800 s | 1750 s ≈ 29 min | **≈ 42 min** |

要点：
- RTT 小时（≤2ms），带宽是绝对主导，**优化往返收益约 15%**；
- RTT 变大或**文件数多而单文件小**（如大量截图/缩略图），固定开销会迅速超过传输时间，此时优化往返收益可达 **40%+**；
- 源端读取（SAF `ContentResolver.OpenInputStream`，走 Binder IPC、无缓冲包装）与网络写入**完全串行**在 `_gate` 内，读取时间无法被网络时间掩盖。

### 3.3 关键发现：并行度是假象

`SmbFileStorage` 所有操作过 `_gate`（`SmbFileStorage.cs:36`），且 `CopyFromAsync` 的**源端读取也在锁内**（`SmbFileStorage.cs:228`）。因此：

- `Parallel.ForEachAsync(…, MaxDegreeOfParallelism = 4)` 的 4 个任务只是排队抢同一把锁；
- 吞吐 = 单流吞吐，且**读取与写入零重叠**；
- 设置页的"执行并发数"（`SettingsViewModel.cs:152`，FR-A8.4）在 SMB 下对吞吐没有任何影响，属于误导性 UI。

单流吞吐上限粗估：`chunk / (RTT + chunk/带宽)`，chunk 取 `min(MaxWriteSize, 1MB)`：

| RTT | chunk=1MB 单流上限 | chunk=64KB（SMB 2.0.2 协商） |
|-----|------------------|---------------------------|
| 2 ms | ≈ 45 MB/s | ≈ 22 MB/s |
| 10 ms | ≈ 33 MB/s | ≈ 6 MB/s |

→ **确认服务器协商到的 MaxWriteSize 是首要检查项**：若协商到 64KB，弱网下吞吐会掉一个数量级。

## 4. 后台化方案

### 4.1 方案对比

| 方案 | 优点 | 缺点 | 结论 |
|------|------|------|------|
| **A. `dataSync` 前台服务** | 常驻通知 + 高进程优先级；与 Avalonia UI 同进程，进度回传简单；可随时取消/停止；不受 Doze 网络限制 | Android 15+ 有 **24 小时内累计 6 小时**配额（targetSdk 36 命中），超时必须 `stopSelf` 否则抛 `RemoteServiceException`；需 `POST_NOTIFICATIONS` | **推荐主方案** |
| B. 用户发起的数据传输作业（UIDT / `setUserInitiated(true)`） | 官方推荐的 dataSync 替代；不受 App Standby 配额限制；无 6 小时硬上限 | 必须在应用可见时调度；用户在任务管理器点"停止"会**直接杀进程且不回调 `onStopJob`**；系统按 `setEstimatedNetworkBytes` 判断"跑太久"可随时停；国内 ROM 调度时机不可控 | 作为 A 的**降级/补充**路径，不单独采用 |
| C. WorkManager | 约束（充电/WiFi）完善、系统友好 | 不适合需要长时间保持 SMB 会话的连续大文件流；15 分钟最小周期与配额 | 不适合 |
| D. 仅延长 WakeLock | 改动最小 | 不解决进程被杀、不解决 Doze 网络限制、用户无感知 | 不推荐 |

### 4.2 目标架构

```
                      [进程级，生命周期 = Application]
  OrganizeJobHost（单例）
    ├─ 当前任务状态（阶段 / 进度 / 计数 / 状态文本 / 结果）
    ├─ CancellationTokenSource        ← 从 VM 上移下来，Activity 重建不失效
    ├─ IProgress<…>（节流后）→ 同时喂给 UI 与通知
    └─ 直接调用 Core：OrganizeSession.AnalyzeAsync / ExecuteAsync
         ↑ 启动/停止                     ↓ 进度/完成
  OrganizeForegroundService(dataSync)          Activity 在前台时：
    ├─ StartForeground(id, notif, TypeDataSync)   MainViewModel 订阅 host 刷新 UI
    ├─ 通知：进度 + 已用时长 + 「停止」Action     Activity 不在前台：只更通知
    ├─ OnTimeout(int, ForegroundService) → 存进度 + stopSelf()   ← API 35+ 强制
    └─ WakeLock + WifiLock（FULL_HIGH_PERF）      ← 锁屏后防 WiFi 降功率

  [Manifest 补充]
    FOREGROUND_SERVICE
    FOREGROUND_SERVICE_DATA_SYNC
    POST_NOTIFICATIONS（Android 13+ 运行时动态申请）
    <service android:foregroundServiceType="dataSync" android:exported="false" />
```

关键约束（targetSdk 36 已命中，必须实现）：

- `[Service(ForegroundServiceType = ForegroundService.TypeDataSync, Exported = false)]`
- `StartForeground(id, notification, ForegroundService.TypeDataSync)`
- 覆写 `OnTimeout(int startId, ForegroundService fgsType)`（`ApiSince=35`）：几秒内保存进度并 `stopSelf()`，否则系统抛 `RemoteServiceException` 崩溃
- 运行时申请 `POST_NOTIFICATIONS`，否则通知不显示（用户会以为没在跑）
- 需要 `Xamarin.AndroidX.Core` 包引用（`NotificationCompat.Builder`）
- 荣耀/华为机型：额外引导用户加入电池优化白名单与后台保护，否则锁屏后仍可能被杀

### 4.3 断点续传（M2，依赖 §1 结论 5 的解锁）

跨会话执行的硬阻塞在于 `analysis-result.json` 不含 `MediaFile.Source`。解锁方式：

1. 新增平台抽象 `IMediaSourceResolver`：`TryResolve(string identifier, out IMediaSource)`；
   - Android：`content://…` → `AndroidSafMediaSource`（用 `ContentResolver` 重建）；绝对路径 → `LocalMediaSource`（需全局存储权限）；
   - 桌面：`LocalMediaSource`。
2. 落盘 `job.json`：`{ 计划参数（level/operation/existAction/fixMtime/outputProfile）、文件清单、完成集合、失败集合、开始时间 }`；
3. 每完成 N 个文件（如 20 个）或每 5 秒批量落盘一次，避免逐文件写盘；
4. 服务 `OnStartCommand` / 冷启动时检测未完成任务 → 通知栏提示"上次有 N 个文件未完成，是否继续"；
5. 续跑前先扫描目标端已存在文件及其大小（可与 §5 的预枚举优化合并），命中则跳过。

> 注意：默认 skip 策略下即使不做 M2，重跑也**不会重传**已完成文件，只是重走一次 Exists 检查（网络目标下每文件 2 个往返）。M2 对 **overwrite / rename 策略**才是刚需。

## 5. 提速项（与后台化正交，按性价比排序）

| 优先级 | 优化 | 预期收益 | 改动位置 |
|--------|------|---------|---------|
| P0 | **埋点测量**：单文件分三段计时（元数据 / 读源 / 写网），执行结束输出聚合摘要（均值、P95、总量）并在日志与状态栏显示 | 得到真实瓶颈，避免盲目优化 | `FileOperator.TransferWithRetryAsync`、`FileOperationResult` |
| P1 | **SMB 目录创建缓存**（照搬 `WebDavFileStorage._knownDirs`） | 省 3~4 往返/文件（固定开销 -25%） | `SmbFileStorage.CreateDirectoryAsync` |
| P1 | **打印协商 `MaxWriteSize`** 到日志；若协商到 64KB，考虑显式请求 SMB 3.x dialect | 弱网下可避免吞吐掉一个数量级 | `SmbFileStorage.EnsureConnected` |
| P2 | **目标目录预枚举**：执行前用一次 QUERY_DIRECTORY 建立"路径 → 大小"索引，替代逐文件 `ExistsAsync` + `GetLengthAsync` | 省 5 往返/文件（固定开销再 -35%） | 新增 `IFileStorage` 可选能力或 Core 层索引服务 |
| P2 | **写入字节数自证大小**：`CopyFromAsync` 已知道写入总量，用它替代 `GetLengthAsync` 校验 | 省 3 往返/文件 | `FileOperator.cs:158` |
| P2 | **去掉 `MoveAsync` 前置 `DeleteIfExists`**：`.mo-tmp` 名唯一，不会撞名 | 省 2 往返/文件 | `SmbFileStorage.cs:273` |
| P2 | **读写流水线**：源端读取移出 SMB 锁，用双缓冲（2 × chunk，约 2MB）让读与写重叠 | 隐藏 `T_read`（SAF 源尤其明显） | `SmbFileStorage.CopyFromAsync` |
| P3 | **修正 UI 语义**：SMB 下并行度无效，要么实现多连接（N 个 `SmbFileStorage` 轮转，改动大），要么把设置项说明改为"仅 WebDAV/本地生效" | 消除误导 | `SettingsViewModel`、`SRS` |
| P3 | **进度节流**：`Progress<double>` 每文件 Post 一次 UI，5000 文件 = 5000 次文本刷新；改为每 200ms 或每 20 个文件更新一次 | 减少 UI 线程抖动 | `WorkbenchViewModel.cs:351` |

优化后固定往返可从 **13~14 降到 2~5**，局域网场景总时长约降 10~15%，高延迟/小文件场景可降 40%+。

## 6. 落地顺序与工作量

| 里程碑 | 内容 | 工作量 | 依赖 |
|--------|------|--------|------|
| **M0 埋点** | 三段计时 + 聚合摘要 + 打印协商 MaxWriteSize | 0.5 天 | — |
| **M1 前台服务** | Manifest 权限（含 `POST_NOTIFICATIONS` 动态申请）、`OrganizeForegroundService`、`OrganizeJobHost`、通知渠道与进度/停止 Action、`OnTimeout` 覆盖、WakeLock+WifiLock 下沉、VM 改为订阅者、电池优化白名单引导 | 1.5~2 天 | — |
| **M3 提速** | P1 全部 + P2 前三项（依据 M0 数据取舍） | 1~2 天 | M0 |
| **M2 断点续传** | `IMediaSourceResolver` + `job.json` + 增量落盘 + 续跑提示 + Core 测试 | 2~3 天 | M1 |
| M4（可选） | UIDT job 降级路径、充电/WiFi 约束调度 | 1 天 | M1 |

建议：**先 M0 + M1（约 2~2.5 天）**，这是把"必须盯着"变成"挂着跑"的关键一跳，风险低且用户体感改善最大；M3 依 M0 数据决定做哪些；M2 视 overwrite/rename 使用频率决定优先级。

## 7. 风险与验证清单

| 风险 | 影响 | 应对 |
|------|------|------|
| Android 15/16 `dataSync` 6 小时配额（官方口径 6h/24h；有二手资料称 Android 16 收紧至 3h，需实测） | 超大批量备份被强制停止 | 实现 `OnTimeout` 保存进度；`adb shell device_config get activity_manager data_sync_fgs_timeout_duration` 实测确认；超配额时降级到 UIDT job |
| 荣耀/华为 ROM 激进杀后台 | 前台服务仍可能被杀 | 电池优化白名单引导；**M2 断点续传兜底** |
| `POST_NOTIFICATIONS` 未授权 | 通知不显示 | 执行前检查并引导授权；未授权时给出 App 内提示 |
| 进程被杀留下 `.mo-tmp` | 目标端垃圾文件 | 现有 `TryDeleteTempAsync` 覆盖失败路径；进程被杀场景可在启动时做一次清理扫描（可选） |
| 长时间运行 OOM（NFR-A2 峰值 ≤300MB） | 崩溃 | 双缓冲控制在 2~4MB；后台化后 UI 可卸载，反而更宽裕 |
| 与桌面端共享 Core 的回归 | 桌面行为变化 | M2/M3 的 Core 改动由 `test/MediaOrganizer.Core.Tests` 覆盖（`FileOperatorTests` / `OrganizeSessionTests` 已存在） |

真机验证清单（Honor PGT-AN10，Android 16 / API 36）：

1. 执行中按 Home 退后台 → 通知栏可见进度 → 传输继续；
2. 锁屏 10 分钟 → 传输继续，吞吐无明显下降（验证 WifiLock）；
3. 通知点「停止」→ 优雅停止，已完成文件保留；
4. 从任务管理器强制停止 → 冷启动后能提示续跑（M2 后）；
5. `adb shell dumpsys activity services <pkg>` 确认服务 `foreground` 状态与 `dataSync` 类型；
6. `adb shell device_config get activity_manager data_sync_fgs_timeout_duration` 记录本机配额；
7. 对比 M3 前后同一批文件的总时长与日志摘要。

## 9. 实施记录（2026-09-05）

按 §6 建议落地 **M0 + M1 + M3**（M2 断点续传与 M4 UIDT 降级本轮未做，配额触顶走优雅停止+通知）。决策采用评估文档推荐项。

### 已实现

**M0 埋点**
- 新增 `Core/Diagnostics/CoreLog.cs` 静态日志出口（组合根接 `AppLogger`）；
- `SmbFileStorage.EnsureConnected` 连接后打印协商 `MaxWriteSize` 与实际写入块（排查弱网吞吐首要检查项）；
- `FileOperator` 逐文件分段计时（元数据 = 碰撞检查+建目录+改名+时间戳；传输 = CopyFromAsync），结果聚合为 `TransferTimingReport`（均值/P95/总字节）随 `FileOperationResult.Timing` 返回，VM 状态栏与日志显示。

**M3 提速**（固定往返 13~17 → 5~6 次/文件）
- `IFileStorage.CopyFromAsync` 返回 `Task<long>`（写入字节数），`FileOperator` 用「写入自证」替代拷贝后 `GetLengthAsync` 重查（省 3 往返/文件，校验语义不变）；
