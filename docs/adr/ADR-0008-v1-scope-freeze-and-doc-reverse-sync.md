# ADR-0008: v1.0 发布范围冻结与需求文档反推修订

- 状态：已接受（Accepted）
- 日期：2026-08-30
- 关联：ADR-0004（网络输出目标）、ADR-0005（Android 分支）、ADR-0007（SMBLibrary）、docs/review/2026-08-30-设计评审.md
- 访谈方式：grill-with-docs 持续追问式访谈（2026-08-30）

## 背景

2026-08-30 的全量评审（`docs/review/2026-08-30-设计评审.md`）暴露出需求文档已无法作为验收基准：

1. **ADR 已推翻 SRS，但 SRS 从未同步**。ADR-0007 改用 SMBLibrary 纯托管客户端，直接作废了 SRS 的 FR-10.3（SMB 走 UNC）、FR-10.9（macOS/Linux 需自行挂载）与 R-6（"后续评估 SMBLibrary"），三处至今仍是旧文字。
2. **规格里写死了错误的技术参数**。FR-10.6 / FR-A9.5 / FR-A9.7 三处规定"8MB 分块"，但 SMB 的单次写入上限是 `min(服务器 MaxWriteSize, 1MB)`，且 SMBLibrary 的 `WriteFile` 不自动分片——按规格实现必然 100% 失败。该缺陷于评审当日修复。
3. **两份 SRS 的基准地位不明确**。`SRS.md` §2.2 运行环境只列 Windows/macOS/Linux，完全不含 Android；而项目实际已投入主要精力于 Android 端。
4. **桌面版 UI 形态与规格不符且已稳定**。SRS §4 与 FR-9.1 描述"主窗口三区块 + 六菜单（文件/配置/视图/语言/帮助/报告）"，实际形态为"左侧 220px 导航 + 单页内容区 + 底部状态栏"，且该形态已被接受。
5. **NFR 实测未达标**：行覆盖 62.25%（NFR-6 要求 ≥70%）；APK 50.0 MB（NFR-A3 要求 ≤40MB）。

核心问题：文档是先写的理想形态，代码是后长的现实形态，二者已分叉。继续按文档追代码，意味着要补做菜单栏、resx 国际化等无人需要的工作；反之按代码改文档，则需求文档重新可用。

## 决策

### 1. 双端均为 v1.0 发布目标

桌面版（Avalonia / Windows）与 Android 版同为正式发布目标，不降级其中任何一方。Android 版不因其为后起分支而被视为"移动端附属品"，桌面版也不因其形态未达早期想象而被砍。

### 2. 桌面版 UI 形态冻结在现状

桌面版外观**基本保持现状**，不做形态级改造。据此反推修订规格：

- **FR-9.1 菜单栏删除**。导航形态以现状"左侧导航 + 内容区 + 状态栏"为准写入 SRS。理由：该形态已覆盖全部功能入口，补菜单栏属纯增量工作量且无用户价值。
- **FR-9.4 语言切换 / NFR-8 国际化（resx 文本外置）删除**。v1.0 单一中文界面。理由：本项目面向自用与开源小众场景，多语言投入产出比不成立（与 2026-08 用户既有判断一致，此前仅口头决定，本 ADR 正式记录）。
  - 保留约束升级为 NFR-8'：**UI 文本不得散落在业务逻辑层**，须集中在 View/XAML 或 VM 的可枚举位置，以便将来若重启国际化时可低成本外置。
- **FR-7 魔术工具保留**（桌面端已有实现），其 FR-7.7 局部滚动等细节问题归入"潜在错误修复"批次处理，不影响本决策。

### 3. 文档治理原则：代码现状为准，文档服从代码

- 当规格与实现冲突时，**默认判定为规格过期**，修订规格而非改代码——除非该冲突本身属于待修缺陷（如 8MB 分块属缺陷，改代码）。
- 判别标准：该条款**是否有用户可感知的价值**。有价值而缺失 → 记为需求缺口；无价值而仅因早期设想而存在 → 删除条款。
- `SRS.md` 与 `SRS-Android.md` 维持"主文档 + 平台增补"结构：**`SRS.md` 为双端共同基线**，`SRS-Android.md` 只写 Android 差异与专属条款，不复制 FR 全文（当前 FR-2/FR-A2、FR-5/FR-A5 的大段重复是漂移源头）。
- ADR 引入 **"已被取代（Superseded）"** 状态：被后续 ADR 推翻的 ADR 须在文件头标注取代者与取代范围，不再一律保持"已接受"。首批适用：ADR-0004 的 UNC 部分被 ADR-0007 取代。
- NFR 指标须标注**实测值**。指标未达标时不静默下调，而是在 SRS 中并列"目标值 / 实测值 / 处置（补齐 or 接受并说明理由）"。

### 4. 下一阶段优先级：性能与潜在错误修复优先于新功能

v1.0 收尾阶段以**打磨性能、修复潜在错误**为第一优先级，暂停新功能开发。评审列出的高严重度缺陷（内置模式失效、未来日期误判、SMB 连接泄漏、WebDAV 并发不安全、config 非原子写、SAF 数据双写）均在此列，修复须附回归测试。

### 5. NFR 指标按实测重定

| 指标 | 原值 | 实测 | 处置 |
|------|------|------|------|
| NFR-A3 APK 包体 | ≤ 40 MB | 50.0 MB | **放宽至 ≤ 60 MB**。理由：ADR-0007 曾预估 SMBLibrary"体积影响 < 1MB、NFR-A3 不受影响"，实测不成立；包体增长主因为自包含运行时 + Magick.NET + Avalonia。40MB 非用户可感知指标，60MB 仍属侧载 APK 合理区间。若后续需压缩，走 NativeAOT 或移除 Magick.NET（记为技术债，不阻塞 v1.0） |
| NFR-6 行覆盖 | ≥ 70% | 62.25% | **保留 70% 目标，列为技术债**。本阶段先补齐高严重度缺陷的回归测试与 SMB/WebDAV 存储层测试，覆盖率随缺陷修复自然提升；不因未达标而下调指标 |
| NFR-11 WebDAV 超时 | 30s 可配 | 未实现（HttpClient 默认 100s） | 本阶段补上，属"潜在错误修复" |
| NFR-A7 Android 测试 | Android 专属逻辑在项目内测试 | 无测试项目 | 列为技术债，v1.0 不引入 Android 测试宿主；Android 专属逻辑改为尽量下沉到可测的纯函数 |

## 风险

| 风险 | 缓解 |
|------|------|
| "文档服从代码"被滥用为降低质量门槛的借口（凡没做完的就删需求） | 判别标准限定为"是否有用户可感知价值"，且须在本 ADR 的"后果"表中逐条列明删除项，接受复查；缺陷类冲突一律改代码而非删需求 |
| 桌面 UI 冻结后被误读为"桌面版不再演进" | 本决策仅冻结**形态**（导航与外壳结构），功能补齐与缺陷修复照常进行 |
| 删除国际化后若未来需重启，重构成本上升 | NFR-8' 约束 UI 文本集中在可枚举位置，届时外置成本可控 |
| 包体放宽至 60MB 后失去约束，持续增长 | 60MB 为硬上限；超限须先评估 NativeAOT / 移除 Magick.NET，不得再次无条件放宽 |
